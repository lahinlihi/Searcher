# Searcher 제품 계약서

작성 2026-11-18, 수정 2026-11-24.

- **1부 — 사례로 배우는 점수**: 승인 2026-11-20, 구현·운영 적용 2026-11-23.
- **2부 — 뉴스레터 편집실 통합과 회사별 맞춤** (문서 끝): **승인 대기** (승인 전에는 구현하지 않는다).

## 0. 제품이 가려는 곳

- 공사·물품을 뺀 **용역 사업 전반**(교육·HR뿐 아니라 기술개발, AI, 해외사업 등)을 다루는 종합 플랫폼.
- 낙찰률 분석은 하지 않는다.
- 사람이 고민하고 판별하는 부분을 AI로 줄인다.

순서는 사용자가 정했다: **맞는 공고 찾기가 먼저, 공고 분석(과업·정량점수·비용·수행실적)은 그다음.**
이 문서는 1차인 "맞는 공고 찾기"만 계약한다. 뒤 단계는 7절에 순서만 적는다.

## 1. 1차의 의도 — 왜 하는가

사용자가 가장 자주 듣는 말이 "왜 이 공고가 안 나왔지?"다. 키워드에 없어서 빠진 경우도 있지만,
**키워드에 있는데도 점수가 낮게 나온 경우가 많다.** 적합 공고를 고르는 일은 지금 개인 감각에 기대고 있고,
그 감각이 시스템에 옮겨지지 않는다. 놓친 사례를 꾸준히 반영할 길이 필요하다.

### 조사로 확인한 사실 (2026-11-18, 계정 5번의 북마크 28건 기준)

| 항목 | 값 |
|---|---|
| 북마크 공고의 현재 점수 중앙값 | 35.3점 (최소 5.0, 최대 50.8, 60점 이상 0건) |
| 제목에 관심 키워드가 없는 북마크 | 28건 중 4건 — 지금 구조에서는 목록에 오르지 못한다 |
| 유형이 "기타"로 떨어져 유형 점수 0점인 북마크 | 28건 중 10건 |
| 최근 30일 적재 24,542건 중 북마크의 순위 중앙값 (현재 점수) | 1,021등 |
| 같은 조건, 사례 방식(나머지 북마크 중 가장 비슷한 3건과의 평균 유사도) | **393등** |
| 100등 안에 든 북마크 | 현재 2건 → 사례 방식 6건 |
| 500등 안에 든 북마크 | 현재 8건 → 사례 방식 15건 |

원인: 유형 점수가 문구가 맞으면 25점·아니면 0점이고, 키워드 하나는 5~7점뿐이며,
북마크·제외 이력이 점수에 전혀 쓰이지 않는다.

이 측정은 어림값이다. 북마크 28건은 모두 마감이 지났고 27건은 30일보다 전에 적재됐는데, 비교 대상은 "최근 30일 적재분"으로 잡았다.
그 공고가 실제로 경쟁하던 시점의 공고들과 비교한 것이 아니다. 정식 채점은 4.4의 정의를 따른다.

한계도 확인했다. 사례가 28건뿐이라 순위가 2~3배 좋아지는 수준이지 해결은 아니다.
다른 북마크와 닮은 데가 없는 공고(예: SNS 마케팅 운영)는 오히려 순위가 내려갔다.
**사례가 쌓일수록 나아지는 구조**이고, 그래서 놓친 공고를 신고하는 경로가 이 설계의 중심이다.

## 2. 목표와 하지 않을 것

**목표**
1. 놓친 공고를 한 줄로 신고하면, 어느 단계에서 빠졌는지 시스템이 답한다.
2. 신고한 공고와 북마크가 "정답 목록"으로 쌓이고, 점수가 그것을 배운다.
3. 점수 방식을 바꿀 때마다 정답 목록이 몇 등에 오는지 숫자로 잰다. 나빠지면 알 수 있다.
4. 제목에 관심 키워드가 없어도 내가 고른 공고와 비슷하면 화면에 나온다.

**이번에 하지 않는 것**
- 2026년 4월 이전 과거분 적재, 검색 색인, 조달 분류 코드 필터 (7절의 2차)
- 참여 판단서: 과업 분석·정량점수·비용·수행실적 (7절의 3차)
- AI(LLM)가 공고를 읽고 판정하는 방식 — 사례 방식으로 추린 상위 공고에 이유를 붙이는 용도로 나중에 검토

**일어나면 실패인 것**
- 지금 잘 나오던 공고가 예고 없이 뒤로 밀린다.
- 나라장터 API 호출이 늘어난다 (이 기능은 API를 부르지 않는다).
- 점수가 왜 그렇게 나왔는지 화면에서 알 수 없다.
- 신고해도 아무 변화가 없다.

## 3. 접근 방식 — 검토한 것과 고른 것

| 방식 | 내용 | 판단 |
|---|---|---|
| A. 점수식 손보기 | 유형 문구·배점을 고친다 | 빠르지만 사례마다 손으로 고쳐야 한다. 지금까지의 방식이고 같은 불만이 반복됐다. 급한 것만 보조로 쓴다 |
| **B. 사례로 배우는 점수** | 북마크·신고 공고와 비슷하면 위로, 제외한 공고와 비슷하면 아래로 | **사용자가 선택.** 신고가 곧 개선이 되고, 키워드에 없는 표현도 잡으며, 추가 비용이 없다. 초기엔 사례가 적어 거칠다 |
| C. AI가 읽고 판정 | 후보 공고를 LLM이 읽고 적합 여부와 이유를 적는다 | 이유가 붙는 장점이 있으나 호출 비용·무료 한도 제약이 있고 판정이 흔들릴 수 있다. 나중에 B 위에 얹는다 |

어느 방식이든 **채점 장치(정답 목록의 순위 측정)를 먼저 만든다.** 이것이 "꾸준히 고친다"의 실체다.

## 4. 핵심 기능

### 4.1 놓친 공고 신고와 진단
공고번호, 주소, 제목 중 하나를 넣으면 DB에서 찾아 아래 중 어디서 빠졌는지 답한다.

| 판정 | 뜻 | 다음 행동 |
|---|---|---|
| 수집 안 됨 | DB에 없다 | 어디서 본 공고인지 메모를 받아 기록 (사이트 추가 판단 자료) |
| 걸러짐 | 제외 키워드에 걸림 / 관심 키워드 없음 / 금액 범위 밖 / 기간 지남 / 직접 제외함 | 걸린 조건을 그대로 보여 준다 |
| 순위 낮음 | 통과했지만 뒤에 있다 | 현재 등수와 점수 내역(키워드·유형·기관·사례)을 보여 준다 |
| 묶임 | 중복·정정공고로 다른 공고에 합쳐졌다 | 합쳐진 공고를 보여 준다 |

"묶임"은 지금 기록으로 알 수 있는 데까지만 답한다: 화면에서 같은 사업으로 묶이는 경우(제목 기준)와 중복 표시가 붙은 행.
수집 단계에서 버려진 중복은 기록이 없어 "수집 안 됨"으로 나온다. 이를 위해 수집 저장 경로를 고치지는 않는다 (작성자 판단).

판정과 등수는 **대시보드 기준**으로 계산한다 (관심 키워드 필터, 제외 목록 적용). 검색 화면은 관심 키워드로 거르지 않고,
메일 입찰동향은 별도 키워드 묶음을 쓰므로 판정이 다를 수 있다. "안 나왔다"는 대시보드 이야기다 (사용자 확인, 2026-11-20).

화면 예시:

```
[놓친 공고 신고]  2026년도 IT역량교육과정 위탁운영            [찾기]

 찾음: 나라장터 API (용역) · 2026-11-03 적재
 판정: 순위 낮음 — 같은 주에 올라온 통과 공고 1,100건 중 930등 (8.5점)   ← 숫자는 예시
   키워드  3.5  "교육"이 "IT역량교육과정" 안에 묻혀 있음
   유형    0    정해 둔 유형 문구와 맞지 않아 "기타"
   기관    5
   사례    —    아직 반영 전
 [정답 목록에 넣기]   넣으면 사례 점수 기준 28등 예상
```

신고한 공고는 정답 목록에 들어가고 북마크와 같은 무게의 사례가 된다.

### 4.2 사례 점수
- **사례**: 북마크와 신고 공고가 좋은 사례다. 열람 기록은 쓰지 않는다 (눌러 본 것과 좋은 것은 다르다 — 작성자 판단).
- **나쁜 사례는 1차에서 점수에 쓰지 않는다** (작성자 판단). 4.3 구역의 [아님]은 그 공고를 숨기고 기록만 남긴다.
  이유: 감점이 맞는지 잴 지표가 아직 없고, 기존 제외 이력(계정 3번 56건)은 주제가 아니라 금액·지역 때문에 누른 것일 수 있다. 기록이 쌓이면 다음 차수에서 다룬다.
- **계산**: 공고 제목을 벡터로 바꿔 두고, 좋은 사례 중 가장 비슷한 3건과의 평균 유사도를 점수로 삼는다. 지금 쓰는 한국어 모델(`jhgan/ko-sroberta-multitask`)을 그대로 쓴다.
- **사용자별**로 계산한다. 좋은 사례가 5건 미만인 사용자는 지금 점수를 그대로 쓴다 (작성자 판단).
- **벡터 저장**: 공고를 수집할 때 한 번 계산해 저장한다. 지금은 화면을 열 때마다 계산한다. 기존 약 15만 건은 한 번에 채운다 (측정상 24,542건에 268초 → 전체 약 27분, CPU).
- 점수 옆에 **가장 비슷한 사례의 제목**을 보여 준다. "왜 이 점수인가"의 답이다.

### 4.3 "키워드엔 없지만 비슷한 공고" 구역
대시보드에 구역을 하나 더한다. 관심 키워드 검사를 통과하지 못했지만 사례 점수가 높은 공고를 날마다 위에서 몇 건 보여 준다.
각 줄에 [좋음](정답 목록에 넣기)과 [아님](제외)을 둔다. 누를 때마다 사례가 늘어난다.

### 4.4 채점
정답 목록(북마크 + 신고)의 공고가 후보 전체에서 몇 등인지를 방식별로 잰다.
잴 때는 그 공고 자신을 사례에서 빼고 계산한다 (자기 자신과 비교하면 항상 1등이 되기 때문).

후보의 정의 (작성자 판단):
- 정답 공고마다, **그 공고가 적재된 날 앞뒤 7일 안에 적재된 공고**를 후보로 삼는다. 그때 화면에서 경쟁하던 공고들이다.
- 결과공고는 뺀다. 마감 여부는 따지지 않는다 (지난 정답도 잴 수 있어야 한다).
- 숫자를 두 가지로 낸다. ① 관심 키워드로 거르지 않은 전체 후보 중 등수 — 키워드가 없는 정답은 현재 방식에서 0점으로 친다.
  ② 관심 키워드를 통과한 후보 중 등수 — 정답도 통과한 것만 센다. 4.5의 전환 판정은 ②를 쓴다.
결과(순위 중앙값, 100등 안 건수, 500등 안 건수, 사례 수)를 날짜와 함께 저장해 추이를 본다.

### 4.5 목록 정렬 전환 — 증거가 있을 때만
기존 목록·대시보드의 정렬은 **바로 바꾸지 않는다.** 프로젝트 규칙(안정 동작 코드 수정 금지)에 따른다.
- 처음에는 사례 점수를 기존 점수 옆에 **함께 보여 주기만** 한다.
- 켜도 관심 키워드 필터는 그대로다. 키워드가 없는 공고는 4.3 구역에만 나온다. 바뀌는 것은 통과한 공고들의 순서뿐이다 (작성자 판단).
- 적용 화면은 **대시보드만**이다. 검색 목록과 메일 입찰동향은 건드리지 않는다. 검색 목록은 대시보드에서 효과가 확인된 뒤 다음 차수에서 다룬다 (작성자 판단).
- 사용자별로, 채점(4.4의 ②)에서 사례 방식의 순위 중앙값이 현재 방식보다 좋을 때 그 사용자가 설정에서 "사례 점수로 정렬"을 켤 수 있다. 끄면 원래대로 돌아간다.
- 사전 측정에서 "사례 절반 + 규칙 절반"은 중앙값 901등으로 사례만 쓴 393등보다 나빴다. 섞는 비율은 채점으로 정한다.

## 5. 사용자 흐름과 수용 기준

**흐름 1 — 놓친 공고 신고**
공고번호·주소·제목 입력 → 후보에서 선택 → 판정과 근거 확인 → 정답 목록에 넣기.
- DB에 있는 공고는 네 판정 중 하나와 근거(걸린 조건 또는 등수·점수 내역)가 나온다.
- DB에 없는 입력은 "수집 안 됨"으로 기록되고 출처 메모를 남길 수 있다.
- 정답 목록에 넣은 직후 그 사용자의 사례 점수에 반영된다 (서버 재시작 없이).
- 판정은 그 사용자의 실제 설정(관심·제외 키워드, 금액 범위, 제외 목록)으로 계산한다.

**흐름 2 — 비슷한 공고 구역에서 고르기**
대시보드 → 구역의 공고 확인 → [좋음] 또는 [아님].
- 구역의 공고는 모두 관심 키워드 검사를 통과하지 못한 공고다 (통과한 공고는 기존 구역에 있다).
- 마감이 지난 공고, 결과공고, 이미 북마크·제외한 공고는 나오지 않는다.
- 각 줄에 가장 비슷한 사례의 제목이 보인다.
- 좋은 사례가 5건 미만이면 구역 대신 "사례를 5건 이상 모으면 켜집니다" 안내가 나온다.

**흐름 3 — 채점 보기**
채점 화면 → 방식별 순위 중앙값·100등 안 건수·추이 확인.
- 현재 방식과 사례 방식이 같은 정답 목록, 같은 후보로 나란히 나온다.
- 신고 건수가 판정별로 집계된다 (수집 안 됨 / 걸러짐 / 순위 낮음 / 묶임).

**흐름 4 — 정렬 전환**
설정 → "사례 점수로 정렬" 켜기/끄기.
- 채점 결과가 현재 방식보다 좋지 않으면 켤 수 없고 이유가 표시된다.
- 끄면 목록 순서가 전환 전과 같다.

**공통**
- 새로 수집된 공고는 수집 직후 벡터가 저장된다. 벡터 저장이 실패해도 수집은 성공으로 끝나고 실패는 로그에 남는다.
- 임베딩 모델을 불러오지 못하면 사례 점수 없이 기존 화면이 그대로 동작한다.
- 이 기능 때문에 나라장터 API 호출이 늘지 않는다.

## 6. 반드시 통과해야 하는 시나리오

1. **유형 0점 공고**: "2026년도 IT역량교육과정 위탁운영"을 신고 → "순위 낮음"과 유형 0점 내역이 나온다 → 정답 목록에 넣는다 → 채점의 정답 수가 1 늘어난다.
2. **키워드 없는 공고**: "2027년 공공앱 운영관리 용역"(관심 키워드 없음)을 신고 → "걸러짐: 관심 키워드 없음" → 정답 목록에 넣는다 → 제목이 비슷한 다른 공고가 "비슷한 공고" 구역에 나타난다.
3. **DB에 없는 공고**: 없는 공고번호를 신고 → "수집 안 됨" → 출처 메모 저장 → 채점 화면의 "수집 안 됨" 집계가 1 늘어난다.
4. **제외 반영**: 구역에서 [아님]을 누른다 → 그 공고가 구역에서 사라지고 다시 나오지 않는다. 다른 공고의 점수는 변하지 않는다.
5. **되돌리기**: "사례 점수로 정렬"을 켰다 끈다 → 목록 순서가 전환 전과 같다.
6. **기존 동작 보존**: 사례가 없는 계정으로 대시보드·검색을 연다 → 응답이 이 기능 도입 전과 같다.
7. **재현성**: 계정 5번의 북마크 28건으로 채점을 돌린다 → 사례 방식의 순위 중앙값이 현재 방식보다 좋다 (사전 측정: 393등 대 1,021등, 후보 구성에 따라 값은 달라질 수 있다).

## 7. 그다음 순서 (이 계약의 범위 밖)

- **2차 — 넓게·빠르게 찾기**: 조달 분류 코드·지역 제한·계약 방법 필터, 검색 색인, 2026-04 이전 과거분 적재(7일 단위 API 한도 준수), 분야별 프로필.

# 2부 — 뉴스레터 편집실 통합과 회사별 맞춤

작성 2026-11-24. 상태: **승인 대기**.

## 11. 의도 — 왜 하는가

**최종 모습(사용자):** 회사마다 관심사만 등록해 두면, 그에 맞는 정보를 "알아서" 골라 회사별로 다른 메일을 보내는 서비스.
지금은 테스트 단계다. 관심사는 원래 회사에게 받아야 하지만 지금은 운영자가 지정해 두었고(입찰동향 조건), 모두에게 같은 메일이 간다.

**지금의 불편(사용자):**
- 메일 하나를 만드는 데 화면이 세 곳이다 — 기사 시사점(`/newsletter/review`), 공고 조건(`/newsletter/brief`), 발송(`/newsletter/send`).
- 이미 만든 기사와 이미 분류된 공고를 모으기만 하면 되는데 오래 걸리고 오류가 계속 난다.

**조사로 확인한 원인 (2026-11-23):**
- 메일 구성 자체는 새로 생성하지 않는다. 저장본이 있으면 0.4초, 크롤 뒤 재계산 5.7초, 서버 재시작 직후 29.8초(제목 분석 모델 로딩).
- 오래 걸리는 것은 화면의 AI 버튼이다. 편집실 "지금 생성"은 07:30에 만든 시사점을 처음부터 다시 쓰고(1~5분, 검수 전 항목은 고친 문장까지 덮어씀), 입찰동향 "지금 분류"는 크롤 뒤 자동 분류가 없어 매일 미분류 100여 건 경고가 뜨고 누르면 100~120초 걸린다.
- ht-search.com 은 Cloudflare 를 거치며 100초가 넘는 요청을 끊는다(화면에는 "HTTP 524"). 서버는 뒤에서 계속 돈다. 실제 발송도 받는 사람마다 메일 서버에 접속하므로 구독자가 늘면 같은 문제가 난다.
- 서버 로그는 재시작마다 덮어써져 과거 오류 기록이 없다. (화면에 뜬 문구는 사용자 확인 전 — 추정)

## 12. 목표와 하지 않을 것

**목표**
1. 메일 만들기를 **한 화면**에서 한다: 시사점 확인·승인 → 받는 사람별 공고 확인 → 미리보기·발송.
2. 메일을 만들 때 **AI 를 다시 부르지 않는다**. 이미 만든 시사점과 이미 분류된 공고를 모은다.
3. 100초를 넘을 수 있는 작업은 **서버 뒤에서 돌리고** 화면은 진행 상황만 본다. 화면 오류로 끊기지 않는다.
4. **자동 발송**을 켜고 끌 수 있다(기본 꺼짐).
5. **받는 사람(회사)마다 관심사**를 둔다. 기본 관심사 하나 + 회사별로 바꾼 항목만 따로. 다른 회사 설정을 복사해 시작할 수 있다.
6. 누구에게 **무엇을 보냈는지** 받는 사람별로 남는다.
7. **회사별 화면**(원하는 정보 + 받은 것)과 **전체 화면**(어떤 회사들이 무엇을 원하는지)으로 모니터링한다.

**이번에 하지 않는 것 (사용자 결정: 다음 단계)**
- 반응 수집(메일 속 공고 클릭, "관심 있음·없음") — 구독 동의 문구 정비가 먼저다.
- 회사가 직접 관심사를 고치는 개인 링크.
- 시사점(기사)의 회사별 맞춤 — 이번에는 시사점은 모두에게 같다. 구조만 회사별로 나눌 수 있게 둔다.
- "설정한 관심사와 실제 반응이 어긋나는 회사" 표시 — 반응 데이터가 있어야 한다.

**일어나면 실패인 것**
- 같은 발행일 메일이 한 사람에게 두 번 간다 (지금의 중복 발송 방지는 그대로 유지).
- 자동 발송이 꺼져 있는데 메일이 나간다. 직접 "제외"한 시사점이 자동 발송에 실린다.
- 회사 A 의 관심 공고가 회사 B 에게 간다.
- 미리보기에서 본 공고와 실제로 나간 공고가 다르다 (받는 사람별로도 같아야 한다).
- 화면을 합치면서 실제 발송의 확인 문구(SEND / RESEND)가 사라진다.

## 13. 접근 방식 — 검토한 것과 고른 것

| 방식 | 내용 | 판단 |
|---|---|---|
| **A. 구독자마다 관심사 (기본값 + 덮어쓰기)** | 지금의 입찰동향 조건이 "기본 관심사"가 되고, 회사마다 바꾼 항목만 저장. 메일은 받는 사람마다 공고 칸을 따로 만든다 | **사용자 선택.** 회사별 맞춤이 바로 되고, 대부분 기본값을 쓰면 관리할 일이 적다 |
| B. 관심 묶음(그룹)에 구독자 배정 | "교육·HR", "AI·기술개발" 묶음에 회사를 넣는다 | 같은 묶음 안에서 회사별로 다르게 못 한다 |
| C. 조건 하나 유지, 회사별은 나중에 | 통합·자동 발송만 먼저 | 곧 메일 구성·발송을 다시 뜯어고치게 된다 |

사용자 질문 "회사가 늘면 다 따로 관리해야 하나?"에 대한 답으로 정한 것: 기본값만으로 나가고, 운영자가 손대는 것은 기본값과 다르게 받아야 하는 회사뿐이다. 다음 단계의 개인 링크·반응 학습이 붙으면 그 예외도 회사 쪽이 채운다.

## 14. 핵심 기능

### 14.1 통합 편집실 `/newsletter`

```
뉴스레터                         발행일 [11/24 ▾]   자동 발송 [꺼짐 ○] 08:30
① 기사 시사점      07:30 생성 · 검사 통과 3 · 승인 2 · 제외 0        [다시 만들기]
   카드마다: 고치기 · 근거 대조 · 승인 / 제외 (지금 편집실 기능 그대로)
② 받는 사람별 공고   기본 관심사 25건 · 맞춤 1곳
   [기본 관심사 ▾]  ○○교육컨설팅(맞춤) 22건  △△(기본) 25건 ...
   선택한 사람의 공고 목록 · [관심사 고치기] → 회사별 화면
③ 미리보기·발송    받는 사람 [○○교육컨설팅 ▾]  [PC|모바일] 미리보기
   점검: 승인된 시사점 ✓  구독자 2 ✓  발송 계정 ✓
   [테스트 발송: 주소 ____ ]   [실제 발송 — SEND 입력]
```

- 지금 세 화면의 기능은 모두 옮긴다. 옛 주소(`/newsletter/review`, `/newsletter/brief`, `/newsletter/send`)는 새 화면의 해당 단계로 보낸다.
- 메뉴는 "뉴스레터"(이 화면)와 "발송 설정"(계정·구독자, 지금처럼 따로)과 "구독사"(14.5) 셋으로 줄인다.
- 실제 발송 버튼은 ③ 맨 아래에 두고 확인 문구(SEND, 전원 재발송은 RESEND)를 그대로 요구한다. 발송 화면을 따로 두었던 이유(편집 중 실수 발송 방지)는 이것으로 대신한다.

### 14.2 AI 를 다시 부르지 않기

- **공고 분류는 크롤 뒤 자동**으로 한다. 새 후보만 분류한다. 후보는 **모든 받는 사람의 관심사를 합친 것**이고, 기본 관심사 후보를 먼저 분류한다. 한 번에 분류하는 배치 수에 상한을 두고, 남은 것은 다음 크롤에서 이어서 한다 (작성자 판단 — Gemini 무료 한도와 07:30 시사점 생성 보호). 실패해도 크롤 결과에는 영향이 없다. 화면의 "미분류 N건 — 지금 분류" 경고는 자동 분류가 실패해 남은 것이 있을 때만 보이고, 누르면 서버 뒤에서 돈다.
- **제목 분석 모델은 서버 시작 때 미리** 불러온다(시작을 막지 않게 뒤에서).
- **"지금 생성"은 "다시 만들기"로** 바꾼다. 누르기 전에 "승인 전 항목은 고친 내용까지 새 글로 바뀝니다"를 확인받고, 서버 뒤에서 돈다.
- **입찰동향 목록은 저장본**을 쓴다(지금처럼). 받는 사람의 관심사가 다르면 관심사마다 저장본을 따로 둔다. 크롤이 끝나면 다시 계산한다(지금처럼). "다시 계산"도 서버 뒤에서 돈다.
- **미리보기와 실제 발송 사이에 목록이 바뀌면** (작성자 판단):
  - 수동 발송: SEND 를 누를 때 목록이 화면에서 본 것과 다르면 보내지 않고 "목록이 바뀌었습니다 — 다시 확인하세요"를 띄운다. 미리보기 때 목록의 버전(계산 시각)을 발송 요청에 함께 보내 비교한다.
  - 자동 발송: 사람이 보지 않으므로 그 시각의 최신 목록으로 보낸다.
  - 이어 보내기·RESEND·지난 날짜 재발송: 그 날짜에 **처음 보낸 사람이 받은 목록**(받은 것 기록)이 있으면 그 목록을 쓰고, 없는 사람(새 구독자)은 그 사람 관심사의 현재 목록을 쓴다.

### 14.3 서버 뒤에서 돌리기

- 다시 만들기, 수동 분류, 다시 계산, 실제 발송을 **작업**으로 등록하고 바로 응답한다. 화면은 몇 초마다 작업 상태(대기·진행 n/N·완료·실패와 이유)를 본다.
- 같은 종류의 작업이 이미 돌고 있으면 새로 시작하지 않고 그 작업을 보여 준다.
- 서버가 재시작되면 진행 중이던 작업은 "중단됨"으로 보인다. 실제 발송은 지금의 "이어 보내기"로 남은 사람에게만 보낸다(이미 있는 장치).

### 14.4 자동 발송

- 스위치(기본 꺼짐)와 시각(기본 08:30 — 07:30 시사점 생성 뒤, 09:00 크롤 전 — 작성자 판단). 설정은 화면에서 바꾼다.
- 켜져 있으면 그 시각에: 그날 시사점 중 **승인된 것 + 검사를 통과했고 아직 검수 전인 것**을 승인 처리하고 발송한다. 직접 "제외"한 것과 검사에 걸린 것은 싣지 않는다.
- 실을 시사점이 없거나, 발송 계정이 없거나, 이미 그 날짜를 보냈으면 보내지 않고 그 사실을 기록·표시한다.
- 자동 발송도 수동 발송과 같은 중복 방지·받는 사람별 기록을 탄다. 기록에 "자동"이라고 남긴다.
- 자동 발송이 승인 처리한 항목은 누가 승인했는지 "자동"으로 남는다.

### 14.5 회사별 관심사와 모니터링 `/newsletter/subscribers`

**관심사**
- 항목: 지금 입찰동향 조건과 같다(관심 키워드, 제외 키워드, 공고 분류, 마감 이내 일수, 최소 금액, 최소 적합도 점수, 칸별 건수).
- **기본 관심사** = 지금의 입찰동향 조건(이력 포함 그대로).
- 회사별로는 **바꾼 부분만** 저장한다. 회사 화면에는 기본값을 따르는 부분과 바꾼 부분을 구분해 보여 준다. "기본값으로 되돌리기"가 있다.
- **키워드(관심·제외)는 더하고 빼는 방식**이다: 회사 키워드 = 기본 키워드 + 이 회사에 더한 것 − 이 회사에서 뺀 것. 그래서 기본 키워드를 바꾸면 키워드를 손댄 회사에도 반영된다 (작성자 판단 — "대부분 기본값을 쓰고 예외만 관리"라는 사용자 의도에 맞음).
- **나머지 항목(공고 분류, 마감 이내 일수, 최소 금액, 최소 점수, 칸별 건수)은 바꾸면 그 값으로 대체**된다.
- 복사는 "더한 것·뺀 것·대체한 값"을 그대로 복사한다.
- **복사**: 다른 회사의 설정 또는 기본값에서 출발할 수 있다.
- 회사 단위가 아니라 **받는 사람(구독자 주소) 단위**로 둔다. 같은 회사 두 사람이 다르게 받을 수 있다. 화면은 회사명으로 묶어 보여 준다 (작성자 판단 — 지금 구독자 정보에 회사명이 있고, 회사 테이블을 따로 두면 관리가 하나 더 늘어서).

**받은 것 기록**
- 실제 발송(수동·자동)마다 받는 사람별로: 발행일, 실린 시사점(id·제목), 실린 공고(id·제목·칸), 결과(성공·실패와 이유), 발송 방식(수동·자동·이어 보내기).
- 테스트 발송은 이 기록에 넣지 않는다(지금처럼 발송 이력에만).

**회사별 화면**
```
○○교육컨설팅 · 홍길동 · 구독 2026-11-05~ · 맞춤 관심사(3개 항목 변경)
원하는 정보   관심: 교육운영, 직무훈련, HRD (기본값 + 2) | 제외: 공사, 물품 (기본) | 1억 이상 (변경)
최근 받은 것  11/24 성공 — 시사점 3 · 공고 22 [펼치기]
              11/21 성공 — ...
```

**전체 화면 (어떤 회사들이 무엇을 원하는지)**
- 관심 키워드별 회사 수 순위, 키워드를 누르면 그 회사 목록.
- 기본값을 쓰는 회사 / 맞춤 회사 수.
- 최근 발송: 날짜별 받은 사람 수·성공·실패.

### 14.6 로그를 덮어쓰지 않기

- 서버 로그를 재시작마다 덮어쓰지 않고 쌓는다(날짜별 파일 등, 방식은 구현자). 다음에 오류가 나면 원인을 바로 볼 수 있어야 한다.
- CLAUDE.md 의 재시작 절차(로그 경로)를 바꾸게 되면 절차 문서도 함께 고친다.

## 15. 사용자 흐름과 수용 기준

**흐름 A — 수동으로 메일 보내기**
`/newsletter` → ① 시사점 승인 → ② 받는 사람 하나를 골라 공고 확인 → ③ 미리보기 → 테스트 발송 → SEND 입력 → 발송.
- 화면을 여는 데 AI 호출이 없다. 서버 재시작 직후가 아니면 5초 안에 열린다.
- ③ 미리보기에서 받는 사람을 바꾸면 그 사람이 받을 공고가 보인다.
- 실제 발송은 버튼을 누르면 바로 "진행 중"이 되고, 진행 n/N 이 보이며, 100초가 넘어도 화면 오류가 나지 않는다.
- 발송이 끝나면 받는 사람마다 "받은 것" 기록이 생긴다.

**흐름 B — 회사별 관심사 정하기**
구독사 화면 → 회사 선택 → [관심사 고치기] → 항목 변경(또는 다른 회사·기본값에서 복사) → 저장 → 그 회사의 공고 미리보기.
- 저장하면 그 회사 공고 목록이 다시 계산된다. 기본값을 쓰는 다른 회사 목록은 바뀌지 않는다.
- 기본 관심사를 바꾸면 기본값을 따르는 항목에 한해 모든 회사에 반영된다.

**흐름 C — 자동 발송**
편집실에서 스위치 켜기(시각 확인) → 다음 날 그 시각에 자동 발송 → 편집실·구독사 화면에 결과 표시.
- 꺼져 있으면 절대 나가지 않는다.
- 제외한 시사점과 검사에 걸린 시사점은 실리지 않는다.
- 이미 수동으로 보낸 날짜면 보내지 않는다.

**흐름 D — 모니터링**
구독사 화면 → 전체 화면에서 키워드별 회사 수 확인 → 회사를 눌러 원하는 정보와 받은 것 확인.

**공통**
- 크롤 뒤 자동 분류가 실패해도 크롤 결과·크롤 기록 상태는 그대로다.
- 자동 분류·자동 발송은 나라장터 API 를 부르지 않는다. AI(Gemini) 호출은 분류 배치 수만큼만 늘어난다.

## 16. 반드시 통과해야 하는 시나리오

1. **화면 하나**: `/newsletter` 에서 시사점 승인 → 공고 확인 → 미리보기 → 테스트 발송까지 다른 화면으로 가지 않고 끝난다. 옛 주소 세 개는 새 화면으로 간다.
2. **AI 없음**: `/newsletter` 를 열고 미리보기까지 하는 동안 AI 호출이 0회다 (로그로 확인).
3. **긴 작업**: 실제 발송을 구독자 여러 명(시험용 주소)에게 보낼 때, 요청은 바로 응답하고 진행 상황이 갱신되며 끝나면 완료가 표시된다.
4. **회사별 공고**: 구독자 둘 중 하나만 관심 키워드를 바꾼다 → 두 사람의 미리보기 공고가 다르고, 실제로 받은 메일의 공고도 각자의 미리보기와 같다. 바꾸지 않은 사람은 기본값 목록 그대로다.
5. **복사·되돌리기**: B 를 A 의 설정에서 복사해 만들면 공고 목록이 A 와 같다. "기본값으로 되돌리기" 하면 기본 목록과 같다.
6. **받은 것 기록**: 발송 뒤 회사별 화면에 그날 받은 시사점·공고 목록이 보이고, 실제 메일 내용과 같다.
7. **자동 발송**: 켜고 시각을 몇 분 뒤로 → 그 시각에 발송된다. 제외한 시사점은 빠진다. 끄고 다시 시각이 오면 나가지 않는다. 같은 날 두 번 나가지 않는다.
8. **자동 분류**: 크롤이 끝나면 새 후보가 분류되어 "미분류" 경고가 뜨지 않는다.
9. **중복 방지 유지**: 같은 발행일을 다시 SEND 하면 막히고, RESEND 로만 재발송된다.
10. **기존 동작 보존**: 관심사를 하나도 바꾸지 않은 상태에서 만든 메일의 공고 목록이 이 기능 도입 전과 같다.

## 17. 제약

- 시험 발송은 사용자가 정한 시험용 주소로만 한다. 실제 구독자에게는 사용자 확인 없이 보내지 않는다.
- 크롤(09:00·13:00)·HR뉴스(07:30) 시각과 자동 발송 시각이 겹치지 않게 한다.
- Gemini 무료 한도(3.5-flash 하루 20회 등)를 자동 분류가 다 쓰지 않게 한다 — 07:30 시사점 생성이 먼저다.
- 승인 게이트의 원칙("검사에 걸린 항목이 승인되는 경로를 만들지 않는다", insight.set_status)은 자동 발송에서도 지킨다.
- 서버 재시작은 CLAUDE.md 6단계 절차. `hr_news`·`daily_insights` 자료는 지우지 않는다.

## 18. 구현자에게 맡기는 것

# 3부 — 적합도 점수 재정리

상태: **승인됨 · 구현 완료, 운영 반영 전** (2026-11-25 사용자 승인, 같은 날 작업 브랜치 `worktree-design-refresh` 에 구현).
운영 반영(병합·서버 재시작)과 기존 발주처 등록값 이전(`tools/agency_adjust_migrate.py --apply`)은 사용자 승인 뒤에 한다.

## 20. 의도 — 왜 하는가

화면의 적합도가 50점 언저리에 몰려 "그놈이 그놈"으로 보인다. 사용자는 100점 눈금에서 90점대와 30점대처럼 벌어지는 점수,
그리고 "녹색 공고만 가져왔는데 시든 것이 하나 있네"를 색으로 알아보는 화면을 원한다.
발주처는 "등록이 없어서 감점"이 아니라 "등록이 있어서 가점"이어야 하고, 꺼리는 발주처는 점수를 깎고,
수행 중이거나 관계가 좋은 발주처의 공고는 놓치지 않아야 한다.

### 측정으로 확인한 사실 (2026-11-25, DB 사본 2026-11-23, 대시보드 후보 전체)

| | 계정 5 (설정 없음) | 계정 1 (설정 있음) |
|---|---|---|
| 최고점 | 54.6 = 키워드 24.6 + 유형 25 + 기관 5 | 78.4 = 키워드 28.4 + 유형 45 + 기관 5 |
| 키워드 30점 이상 (만점 45) | 0건 | 0건 |
| 기관 점수 | 948건 중 947건이 기본 5점 | 819건 중 809건이 기본 5점 |

- 키워드 하나가 정확히 맞아도 약 7점이라 만점 45에 닿으려면 한 제목에 6~7개가 맞아야 한다.
- 유형은 설정이 없으면 25, 기관은 등록이 없으면 5에 고정된다. 설정하지 않은 계정의 천장은 약 55점이다.
- 숫자만 펴는 조정(키워드 만점 조정 + 배점 환산)은 상위 15건을 그대로 둔다(15건 중 15건 유지). 순위를 바꾸는 것은 사례 점수뿐이다.
- 사례 점수를 50% 섞으면 계정 5 의 담은 공고 28건의 등수 중앙값이 158등 → 90.5등, 15등 안에 드는 것이 1건 → 7건이 된다.
  (같은 28건으로 점수와 검증을 함께 한 값이라 낙관적이다.)

## 21. 목표와 하지 않을 것

목표
- 적합도를 100점 눈금으로 읽을 수 있게 한다: 잘 맞는 공고는 80점 이상, 키워드 하나만 스친 공고는 40점대.
- 담은 공고와 닮은 공고가 위로 오게 한다.
- 발주처는 등록한 곳만 점수를 움직인다. 중점 발주처의 새 공고는 점수와 상관없이 보인다.

하지 않을 것
- 관심 키워드에 걸리지 않는 공고를 대시보드 본 목록에 넣지 않는다(중점 발주처 칸과 "비슷한 공고" 탭은 예외).
- 꺼리는 발주처의 공고를 목록에서 숨기지 않는다. 점수만 깎는다.
- 유형 감지 규칙, 제외 패턴, 키워드 경계 가중치는 바꾸지 않는다.

## 22. 점수 구성

```
기본 점수 = (키워드 점수 + 유형 점수) / (45 + 유형 만점) x 100
규칙 점수 = 기본 점수                         (사례가 5건 미만인 계정)
혼합 점수 = 기본 점수 x 0.5 + 사례 점수 x 0.5   (사례가 5건 이상인 계정)
적합도   = 0~100 으로 자른 (규칙 또는 혼합 점수 + 발주처 가감점)
```

### 22.1 키워드 점수 (만점 45)
- 지금의 가중합(핵심 키워드 2배, 경계 가중치, 제목 길이 보정)은 그대로 쓴다.
- 만점에 닿는 지점만 바꾼다: 정확히 맞은 키워드 약 4개(또는 핵심 2개 + 일반 1개)에서 45점. 시험값 `45 x min(1, x / 3.0)`.
- 예전의 "규칙 60% + 임베딩 40%" 혼합(화면이 뜬 뒤 숫자를 바꾸던 경로)은 뺐다. 화면마다 점수가 달라지지 않게 하고, 닮음은 사례 점수가 맡는다.

### 22.2 유형 점수
- 값은 지금대로(최우선 45 / 선호 35 / 보통 25 / 낮음 15 / 제외 0, '기타' 0).
- 유형 만점 = 그 계정이 준 유형 가중치 중 최댓값, 다만 25 아래로는 내려가지 않는다(가중치를 주지 않은 유형이 25점을 받으므로). 가중치를 하나도 주지 않은 계정은 25.

### 22.3 사례 점수 (0~100)
- 원값은 1부 4.2 와 같다(제목 벡터와 좋은 사례의 유사도 상위 3개 평균, 자기 자신 제외).
- 100점 환산: 유사도 0.35 → 0점, 0.80 → 100점, 그 사이는 직선. 구간은 측정값(후보 중앙 0.551, 담은 공고 중앙 0.705)에서 잡은 것으로, 구현 때 다시 확인한다.
- 좋은 사례가 5건 미만이거나 벡터가 없는 공고는 기본 점수만 쓴다.
- 1부 4.5 의 "사례 점수순 정렬" 전환은 이 혼합으로 대체한다.

### 22.4 발주처 가감점
- 등록하지 않은 발주처: 0 (영향 없음).
- 등록한 발주처: 발주처마다 숫자를 직접 넣는다. 범위 −30 ~ +30. 양수는 가점(중점 발주처), 음수는 감점(꺼리는 발주처).
- 기존 등록값(0~10, 5 기준)은 새 값으로 옮긴다. 옮기는 표를 사용자에게 보여 주고 확인받은 뒤 적용한다.

### 22.5 중점 발주처 칸
- 가점(양수)을 준 발주처의 공고 가운데 아직 안 본 것을 대시보드에 따로 모아 보여 준다. 적합도와 관심 키워드에 상관없이 나온다.
- 마감이 지난 공고와 결과공고는 넣지 않는다. 수집일이 새로운 순으로, 본 목록과 같은 한 줄 모양으로 보여 준다.

### 22.6 색
- 30점 이하 빨강 → 60점 노랑 → 90점 이상 녹색의 고정 눈금(이미 적용). 화면에 나온 공고끼리 견주지 않는다.

## 23. 수용 기준

- 계정 5, DB 사본 기준으로 대시보드 상위 15건의 적합도가 70점 이상이고 최고점이 85점 이상이다.
- 발주처를 하나도 등록하지 않은 계정에서 어떤 공고도 발주처 때문에 점수가 달라지지 않는다.
- +20 을 준 발주처의 공고는 같은 공고의 등록 전 점수보다 20 높다(100 에서 잘림). −30 을 준 발주처의 공고는 30 낮고 목록에서 사라지지 않는다.
- 중점 발주처의 새 공고는 관심 키워드에 걸리지 않아도 중점 발주처 칸에 나온다. 열어 보면 칸에서 빠진다.
- 좋은 사례가 5건 미만인 계정은 오류 없이 기본 점수만으로 정렬된다.
- 적합도 숫자 위에 마우스를 올리면 구성(키워드·유형·사례·발주처)이 보인다. 대시보드·검색·관심공고·상세 화면의 같은 공고는 같은 점수다.

## 24. 반드시 통과해야 하는 시나리오

1. 설정 없는 계정으로 대시보드를 연다 → 상위 공고가 녹색 쪽으로 보이고, 점수 구성에 발주처 항목이 0 이다.
2. 발주처 하나에 +20 을 준다 → 그 발주처 공고의 점수가 오르고, 중점 발주처 칸에 새 공고가 모인다.
3. 발주처 하나에 −30 을 준다 → 그 발주처 공고가 뒤로 밀리고 붉은 쪽 색으로 남아 있다.
4. 공고 5건을 담은 뒤 대시보드를 연다 → 담은 공고와 닮은 공고가 위로 올라오고, 구성에 사례 점수가 보인다.

## 25. 제약과 구현자에게 맡기는 것

- `scoring.py` 는 안정 동작 코드다. 바꾸기 전에 지금 점수와 새 점수의 분포·상위 15건 비교를 다시 뽑아 사용자에게 보여 주고, 실패하는 테스트를 먼저 쓴다.
- 점수를 쓰는 모든 곳(대시보드, 검색, 관심공고, 상세, 놓친 공고 진단, 뉴스레터 공고 선정)이 같은 함수를 지나게 한다. 뉴스레터 선정 기준 점수가 있으면 새 눈금에 맞춰 함께 옮긴다.
- 관심공고 라벨 보너스(+15/+10/+5)는 그대로 두되 100 에서 자른다.
- 맡기는 것: 발주처 등록 화면의 모양, 중점 발주처 칸의 위치와 건수, 점수 구성 표시 문구.

# 4부 — 신규사업 발굴 ("한 발 걸친 공고"와 시험 키워드)

상태: **승인 대기** (2026-11-25 작성). 구현 전.

## 27. 의도 — 왜 하는가

지금 화면은 "하던 사업과 같은 공고"만 올린다(사용자: "조금 스트릭트한 느낌"). 3부의 사례 혼합은 그 경향을 더 세게 만든다.
사용자가 바라는 것은 **우리가 가진 능력으로 갈 수 있는 최대한도**를 넓게 보는 도구다. 터무니없이 먼 것은 아니다.

"한 발 걸친다"의 뜻 (사용자 설명):
- 실적은 **분야 + 수행 형태**로 나뉜다. 예: "마케터 전문인력 양성 교육" = 마케터 + 양성 교육.
- **형태를 지키고 분야를 넓힌다**: 양성 교육에 초점을 두고 다른 분야의 양성 교육을 찾는다.
- **분야를 인접한 쪽으로 한 걸음씩 옮긴다**: 마케터 → 그로스 마케팅(데이터) → AI 도구 → AI 데이터 분석 인력 교육.

### 시험으로 확인한 사실 (2026-11-25, DB 사본 2026-11-23, 계정 5)

- 담은 공고 28건의 수행 형태: 교육운영 9, 콘텐츠개발 5, 행사운영 2, 시설운영 2, 기타 10.
- 진행 중 공고 3,853건 중 관심 키워드에 걸리는 것은 944건. 나머지 2,909건은 지금 화면에 나오지 않는다.
- 그 2,909건 중 해 본 형태와 같은 것은 135건. 담은 공고와의 유사도 0.60 이상이 31건, 0.50~0.60 이 70건.
- 0.60 이상에서는 "첨단 바이오 인재양성 부트캠프", "청년혁신인재 CES 글로벌 기술연수 운영", "공유대학 취업·진로박람회 운영"처럼
  형태는 해 본 것이고 분야가 새로운 공고가 나왔다. 0.60 아래는 시설관리·감리용역 같은 엉뚱한 것이 섞였다(유형 감지가 '구축'·'운영' 같은 말에 넓게 걸린다).
- 관심 키워드와 **같이 나오는 말**로 인접 키워드를 뽑으면 쓸 만한 것(Agent, 이러닝, MOOC, 챗봇, 교과목, DX)과
  엉뚱한 것(연근해어장, 임대아파트, 결빙제거작업)이 섞인다. 관심 키워드가 넓어서(최근 1년 공고의 23%에 걸림) 생기는 잡음이다.
  → 후보는 관심 키워드가 아니라 **담은 공고와 발굴 화면에서 반응한 공고**에서 뽑아야 한다.

## 28. 목표와 하지 않을 것

목표
- 관심 키워드에 걸리지 않아도 "형태는 해 본 것, 분야는 새로운" 진행 중 공고를 따로 보여 준다.
- 공고마다 **걸친 발**(어떤 담은 공고·어떤 형태와 닿는지)과 **새로운 발**(처음 보는 분야의 말)을 적어 준다.
- 키워드를 사람이 승인하는 틀 안에서 돌린다: 제안 → 시험 → 정식 또는 퇴장.

하지 않을 것
- 발굴 결과를 대시보드 본 목록이나 적합도에 섞지 않는다. 화면을 따로 둔다.
- 사람 승인 없이 키워드를 넣거나 빼지 않는다.
- 회의록·외부 문서·AI 호출은 쓰지 않는다(다음 단계, 29.4).

## 29. 핵심 기능

### 29.1 발굴 화면 `/discover` — 한 발 걸친 공고
- 대상: 진행 중이고, 관심 키워드에 걸리지 않고, 숨기지 않았고, 아직 담지 않은 공고.
- 고르는 기준: 수행 형태가 "해 본 형태"(담은 공고에서 2건 이상 확인된 사업 유형)와 같고, 담은 공고와의 유사도가 기준 이상.
  기준은 0.60 에서 시작한다. 화면에서 "가까운 것만 / 조금 더 멀리"를 고를 수 있게 하되 0.50 아래는 내놓지 않는다.
- 한 줄 표시는 대시보드와 같은 모양에, 둘째 줄에 `걸친 발: 교육운영 · "바이오의약품 인재양성 부트캠프…"와 비슷` / `새로운 발: 첨단 바이오` 를 붙인다.
  "새로운 발"은 그 제목에서 담은 공고들에 없던 말이다.
- 같은 새 분야끼리 묶어 보여 준다(묶음 이름 = 가장 많이 나온 새 말). 한 번에 15건, 가까운 순.
- 줄마다 **좋음 / 아님**. 좋음은 사례에 더하고(1부 4.3 과 같은 동작), 아님은 발굴에서만 숨긴다.
- 1부 4.3 의 "비슷한 공고" 탭은 이 화면으로 옮긴다(같은 일을 하는 곳이 둘이 되지 않게).

### 29.2 시험 키워드 — 제안, 시험, 정식 또는 퇴장
- 후보의 출처: 담은 공고, 발굴에서 [좋음]한 공고, 키워드 없이 열어 본 공고의 제목에서 **두 번 이상 나왔고 관심 키워드에 없는 말**.
- 후보마다 근거를 보여 준다: "이 말이 든 진행 중 공고 N건, 그중 지금 키워드로는 안 잡히는 것 M건" + 예시 3건.
  M 이 0 이면 후보로 내지 않는다(넣어도 달라지는 것이 없다).
- 사용자가 [시험해 보기]를 누르면 4주 동안 "시험 키워드"가 된다. 시험 키워드에 걸린 공고는 **발굴 화면의 별도 묶음**에만 나온다.
- 4주 뒤: 그 키워드로 잡힌 공고를 한 번이라도 담았으면 "정식으로 올릴까요?"를 묻고, 열어 본 것도 없으면 물러난다. 물러난 말은 다시 제안하지 않는다(사용자가 되살릴 수는 있다).
- 정식 키워드도 같은 눈으로 본다: 6개월 동안 그 키워드로만 잡힌 공고를 한 번도 열지 않았으면 "정리 후보"로 알려 준다. 빼는 것은 사용자가 한다.
- 걸음을 이어 가기: 시험 키워드가 정식이 되면 그 키워드로 담은 공고가 다시 후보의 출처가 된다. 마케터 → 그로스 → AI 분석처럼 한 걸음씩 넓어진다.

### 29.3 걸음 수 표시
- 발굴 공고에 "한 걸음"(유사도 0.60 이상, 형태 같음) / "두 걸음"(0.50~0.60 또는 시험 키워드로만 걸림)을 적는다. 그보다 먼 것은 보여 주지 않는다.

### 29.4 다음 단계 (이 계약의 범위 밖)
- 회사 프로필: 회의록·수행실적에서 역량과 관심 방향을 뽑아 걸친 발의 근거로 쓴다. 회의록을 외부 AI 로 보낼지부터 정해야 한다.
- 뜨는 주제: 뉴스 보관분에서 늘어나는 주제와 사전규격에 처음 나온 주제를 맞춰 본다.

## 30. 수용 기준

- 계정 5, DB 사본 기준으로 발굴 화면에 공고가 나오고(0건이면 오류로 본다), 나온 공고 가운데 관심 키워드에 걸리는 것이 하나도 없다.
- 모든 줄에 걸친 발과 새로운 발이 적혀 있다. 걸친 발의 담은 공고를 누르면 그 공고가 열린다.
- 담은 공고가 5건 미만이면 "공고를 5건 이상 담으면 발굴을 시작합니다"를 보여 준다. 빈 화면이나 오류가 아니다.
- 시험 키워드를 켜면 대시보드 본 목록과 적합도는 달라지지 않고, 발굴 화면에만 묶음이 생긴다.
- 시험 기간이 끝난 키워드는 정식 승격 질문 또는 퇴장 가운데 하나로 반드시 정리된다. 승인 없이 정식 키워드가 늘지 않는다.
- 사용자가 본 뒤 "터무니없다"고 한 유형(시설관리·감리 등)이 첫 화면 15건에 섞이지 않는지, 적용 전에 실제 목록을 보여 주고 확인받는다.

## 31. 반드시 통과해야 하는 시나리오

1. 발굴 화면을 연다 → 형태는 해 본 것이고 분야가 새로운 공고가 묶음별로 보인다.
2. 한 공고에 [좋음]을 누른다 → 사례에 들어가고, 다음에 열면 그와 닮은 공고가 더 나온다.
3. 키워드 후보에서 [시험해 보기]를 누른다 → 발굴 화면에 그 키워드 묶음이 생기고, 대시보드는 그대로다.
4. 시험 4주가 지난다 → 담은 공고가 있으면 승격을 묻고, 없으면 물러난다.

## 32. 제약과 구현자에게 맡기는 것

- 유형 감지 규칙(`scoring.py`)은 바꾸지 않는다. 발굴 쪽에서 잡음을 거를 말(시설관리, 감리, 유지보수 등)은 발굴 전용 목록으로 둔다.
- 제목에서 말을 뽑는 방법(띄어쓰기 기준으로 충분한지, 형태소 분석이 필요한지)은 구현 때 후보 목록을 실제로 뽑아 보고 정한다.
- 새 벡터 계산을 요청마다 하지 않는다. 저장된 벡터만 읽는다.
- 맡기는 것: 묶음의 모양, 시험 키워드 관리 화면의 위치(발굴 화면 안 / 필터관리), 문구.

## 비로그인 첫 화면 (사용자, 2026-11-24)

지금은 첫 화면부터 로그인이 필요하다(내부용으로 일부러 그렇게 만들었다). 판매를 시작할 때 아래처럼 바꾼다.

- 로그인하지 않은 방문자는 첫 화면에서 **필터 없이, 수집된 모든 공고를 최신순으로** 본다.
- 필터·정렬 같은 기능은 **있는 것처럼 보이게** 둔다. 방문자가 그것을 바꾸려고 누르면 "로그인 후 사용할 수 있는 기능"이라고 알리고 로그인 화면으로 보낸다.
- 공고를 골라 자세히 보려 할 때도 로그인 화면으로 보낸다.

착수할 때 정할 것: 비로그인에게 보여 줄 항목의 범위(금액·기관·원문 링크), 한 번에 보여 줄 건수와 더 보기 방식, 검색창을 열어 둘지, 로그인 화면의 서비스 소개 문구.
